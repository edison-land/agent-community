# RFC 0010 — 重新定位：社区的机会路由

Status: Accepted as the product direction (maintainer decision, 2026-09-22). Phase 1 is implemented as an in-memory demo with an end-to-end evaluation that outside agents can join ([EVAL](../docs/EVAL.zh-CN.md)); a public demo with fictional members and Durable Object storage runs at https://agent-network-demo.zwteam.top (2026-09-22); the FlareMo-backed node is not deployed (the extension needs the new record kinds). It is validated with KOSX before being generalised ([validation plan](../docs/KOSX_VALIDATION_PLAN.zh-CN.md)).
Date: 2026-09-22
Amended by: [RFC 0011](0011-one-focus-point.md)（2026-09-23）——链路不变，但中间的协调交给成员自己的 Agent；`invite_candidates` 和 `form_squad` 由"只能人做"改为"主人可授权代办"，`propose_needs` 拆成 `refine_request` 与 `suggest`。
Supersedes: the positioning in [RFC 0001](0001-name-and-positioning.md) ("open-source agent-native community platform" is now a technical description, not the value proposition). The naming question in RFC 0001 stays open. Reorders the [roadmap](../ROADMAP.md).

## 1. 决定

**The open-source opportunity router for communities.**

**让社群里的每一个需求，都找到能把它做成的人。**

> People bring the judgment. Agents handle the coordination. The network learns from every collaboration.

维护者在 2026-09-22 做了四个决定：

1. 项目要解决的是**社区的供需协调**，不是"让人和 Agent 组成网络"。Agent 是降低匹配与协作成本的工具，本身不是产品。
2. **成员自助使用。** 所有成员都能发需求、完善档案，也能给别人的需求提建议。所以从第一版起就要把接口定义清楚：成员的 Agent 进入网络后，知道自己可以做什么、应该做什么、不能做什么（第 7 节）。
3. **可以用共同大脑里的群聊数据给成员起草档案。** 前提是成员签署成员协议，形式类似其他应用的用户协议（第 6 节）。
4. 第一版只验证一条链路：提出需求 → 理解需求 → 匹配能力 → 找到候选人 → 预沟通 → 本人接受 → 组成小组。**如果这条链路在 KOSX 不产生价值，这个项目就不继续做。**

## 2. 要解决的问题

社区里既有供给，也有需求，但没有把两者对上的机制。

一个几百人的群里藏着很多能力：有人会做海外商务拓展，有人会做设计，有人认识品牌方，有人做过招聘。需求也每天都在出现："有没有人懂香港招聘？""谁能帮忙做个 Demo？""谁认识律师？"

今天连接这两端全靠运气：
1. 群里发一条消息；
2. 刚好有人看到，或者运营刚好记得某个人；
3. @ 他、私聊、拉群，聊很久；
4. 也许能合作起来。

运营实际上在人工充当"路由"：记住谁是谁、谁最近在做什么、谁可靠、谁有空、谁和谁合作过。这在 30 人时可行，100 人时勉强，500 人时开始失效。一个 500 人的群，真正能被调动起来的，可能只是运营记得的几十个人。

KOSX 官网把自己的价值分成三块：Community & Content、People & Network、Projects & Delivery。缺的是中间那一步：怎样从"我们认识很多厉害的人"，变成"需求出现时，这些人真的能被组织起来"。

## 3. 与现有项目的关系，以及不做什么

OpenAgents 已经支持 Codex、Claude、Cursor 等十多种 Agent 接入同一网络，内置了消息、任务委派和发现功能（Apache 2.0）；ANP、A2A 也在做 Agent 之间的身份、发现和通信。**"Agent 能互联"正在变成基础能力。**

我们不在这一层竞争，而是做它上面的协调层：
- 这个需求需要什么能力；
- 社区里谁能做，有什么证据；
- 由谁拍板；
- 交付和验收的结果怎样反过来让下一次匹配更准。

已经实现的 A2A 网关保留，将来作为对接这些网络的接口。

第一版不做：信息流、私信、Agent 社交、钱包、代币、跨社区联邦、市场排名、自己发明协议。

## 4. 谁来用，怎么用

| 角色 | 在第一版里做什么 |
| --- | --- |
| 成员（自助） | 签署成员协议 → 确认或修改系统起草的档案 → 发需求 → 给别人的需求提建议（推荐人选，包括推荐自己；补充缺少的能力；提出澄清问题）→ 收到邀请后回答预沟通问题 → 接受或拒绝 → 在小组里推进和交付 → 验收 |
| 需求方 | 可以是成员，也可以是运营代企业或 KOSX Lab 录入。采纳或修改需求拆解，挑选候选人，最后验收 |
| 运营 | 提供真实需求，检查匹配是否合理，看运营数据。运营不是唯一入口 |
| 成员的 Agent（可选） | 按第 7 节的接口替主人起草、提建议、回答预沟通。凡是约束本人的决定，都必须本人确认 |

"大家一同给建议"是第一等功能：
- 每条建议都署名；
- 被采纳的推荐算作一次贡献，会记入推荐人的证据；
- 即使没有被选中，推荐也能让网络知道"谁认识谁、谁能判断谁"。

## 5. 核心链路（第一阶段）

```text
需求（成员 / 企业 / KOSX Lab / 共同大脑发现的线索）
  → 理解需求：把一句模糊的想法拆成能力需求（需求方可以修改）
  → 匹配：根据档案、已验证的证据、可投入时间和合作方式，给出候选人和理由
  → 社区建议：成员及其 Agent 推荐人选、补充需求
  → 预沟通：候选人（或他的 Agent 起草后本人确认）回答有没有空、能负责什么、有什么限制、需要什么输入
  → 本人接受
  → 组成小组（Squad）：目标、角色、任务
  → 交付物
  → 需求方验收
  → 更新能力证据和合作关系，下一次匹配更准
```

每一步都有明确的决定人。系统和 Agent 只负责提议与整理。

## 6. 成员档案，以及用群聊起草

**档案字段：**
- 经历、能力；
- 资源与人脉（只写描述，不写联系方式）；
- 正在做的项目；
- 每周可投入时间；
- 接受的合作方式：有偿、股份、资源交换、公益；
- 不做什么；
- 可选：绑定的 Agent。

每一条都标明来源：本人填写、群聊起草、Agent 起草，或者交付验证。其中"交付验证"是验收后自动加入的，标为"已验证"。

**来源：**
1. 本人填写。
2. 共同大脑里的群聊（维护者已同意，但有前提）。
3. 本人的 Agent 起草（沿用 RFC 0009 的机制）。
4. 交付和验收记录。

**用群聊起草的规则：**
- **先签署，后起草。** 没有签署成员协议的人，他的群聊不用于起草档案。
- 起草结果先只给本人看。每一条都注明依据，例如"来自你在 3 个话题里的 12 条发言"，本人可以查看对应的原文片段。本人确认或修改后才公开，任何一条都可以隐藏。
- 网络里只保存起草结果和来源引用（话题编号、消息编号）。群聊原文留在共同大脑，不进入网络的存储。
- 本人撤回同意后：档案下线，用于起草的派生数据删除，之后不再起草。
- 只用于档案和匹配，不作他用，也不提供给第三方。

**成员协议至少要写明：**
- 处理哪些数据：成员自己在社区群里的发言；
- 用来做什么；
- 公开范围：只公开本人确认的内容；
- 本人的权利：查看、修改、隐藏、删除、撤回同意；
- 保存多久；
- 谁负责：社区运营方；
- 会用到哪些第三方服务：模型服务商。

协议文本上线前，建议请法律顾问看一遍，以符合个人信息保护相关法规，例如在适用情况下的单独同意要求。本 RFC 不构成法律意见。

## 7. 成员 Agent 的接口约定

**原则：**
- 每个动作都记录"谁做的"（Agent）和"替谁做的"（它的主人）。
- Agent 可以起草、提议、整理。凡是约束本人的事，必须本人确认：接受角色、承诺时间或报酬、公开档案、验收、以本人名义联系他人。

| 动作 | Agent 可以 | 需要本人确认 | 阶段 |
| --- | --- | --- | --- |
| 读网络说明、本人档案和待办 | 是 | 否 | 1 |
| 起草或更新本人档案 | 起草 | 公开前 | 1 |
| 发布需求 | 起草 | 发布前 | 1 |
| 把需求拆成能力需求 | 提议 | 由需求方采纳 | 1 |
| 浏览需求和成员档案 | 按可见范围 | 否 | 1 |
| 给需求提建议：推荐人选、补充需求、提问 | 是，标注为 Agent 所提 | 否；有频率限制 | 1 |
| 回答预沟通问题 | 起草 | 发送前（本人可以设成"按档案自动回答"） | 1 |
| 接受或拒绝邀请，承诺时间或报酬 | 不可以 | 只能本人 | 1 |
| 在小组里更新进展、整理任务、提交交付物 | 是，标注为 Agent 生成 | 否 | 1 |
| 验收、评价、签发能力证据 | 不可以 | 只能需求方本人 | 1 |
| 在本人机器上代为执行任务 | 是 | 逐单确认（已实现，见 RFC 0007、0009） | 2 |
| 与其他 Agent 直接协商 | — | — | 2 |
| 跨社区路由 | — | — | 3 |

**Agent 应该做的：**
- 只代表自己的主人；
- 所有产出都标注是 Agent 写的；
- 按时回应预沟通，例如 48 小时内，超时视为未回复；
- 提建议时写出理由；
- 遵守可见范围，不把网络里看到的需求和档案带出网络；
- 不替主人做承诺；
- 不主动联系网络外的人。

**同一套动作，提供三种形式：**
1. **给 Agent 读的说明**：`/agents.md`（源文件 `docs/agents.md`），写明接入方式、按待办行动的规则、禁止事项和返回码。`/agent-onboarding.md` 仍是第二阶段执行连接器的说明。
2. **机器可读清单**：`/.well-known/agent-network.json`。列出动作、所需权限、哪些要本人确认、频率限制和版本。Agent 读完就知道能做什么。
3. **可调用的接口**：
   - HTTP API `/api/agent/v1/*`；
   - 一个 MCP 服务器，每个动作对应一个工具，Codex、Claude Code 可以直接接入；
   - 待办列表 `GET /api/agent/v1/inbox`：需要回答的预沟通、等待主人决定的邀请、与主人档案匹配的新机会、请求建议的需求。Agent 由此知道"现在该做什么"。

**授权：** 成员给自己的 Agent 签发授权令牌，有有效期、可以撤销、按动作授权（例如只允许"起草档案、提建议"）。这与现有的执行凭证（RFC 0007 里的 `acc_` 与 `aex_`）分开。需要本人确认的动作，在页面上或通知里完成。

## 8. 数据模型

八类对象继续使用：

| 对象 | 第一版的用法 | 需要的改动 |
| --- | --- | --- |
| Human | 成员与档案 | 增加 `profile`，每一条都带来源和验证状态 |
| Capability | 成员的能力（已经支持由人提供） | 能关联到证据 |
| Request | 需求 | 增加能力需求列表、合作方式或预算、阶段（探索或执行）、来源 |
| Workroom | 小组 | 已经支持多人和多个 Agent；增加角色 |
| Artifact | 交付物 | 无 |
| Attestation | 验收，也就是"经验证的能力"的证据 | 能关联到具体的能力需求 |

新增的记录：
- **Match**：候选人及理由，以及它来自系统推荐还是社区建议；状态为 proposed、invited、accepted、declined、expired。
- **Suggestion**：推荐人选、补充需求或提问，署名到人或 Agent。
- **Preflight**：预沟通的问与答，记录是本人写的还是 Agent 写的、本人是否确认过。
- **Consent**：成员协议的签署记录，包括版本、授权范围（例如"允许用群聊起草档案"）、签署和撤回时间。
- **AgentToken**：成员给自己的 Agent 的授权。

合作关系不单独存储，从已验收的小组推导出来。

**对部署的影响：**
- FlareMo 扩展把记录类型列在白名单里（`COMMUNITY_RECORD_KINDS`），新增记录类型必须改扩展。所以交给管理员的补丁要重新生成。**已完成（2026-09-22）**：扩展 `community-objects/0.2.0` 和补丁 v0.2，扩展测试 8/8，FlareMo 全量 949 项通过；本机 FlareMo 上整条路由链路 14/14 通过。
- 用群聊起草档案，需要共同大脑（`kosx-shared-brain`，另一个仓库）提供一个接口，只对签署了协议的成员返回起草依据：话题编号、发言数量、片段。

## 9. 第一版的匹配

1. 用模型把需求拆成能力需求。
2. 召回：关键词加向量检索，在档案、证据和合作方式中查找。
3. 用模型对候选人排序，并写出"为什么是你"。
4. 过滤：只推荐成员资格有效、没有设置"不接此类"的人；每个需求最多推荐若干人，并限制同一个人被打扰的频率。
5. 需求方和运营能看到理由并调整；被推荐的人能看到自己为什么被找。

不做全局评分，也不做公开排名。

**演示版的实现（2026-09-22）**：第 1–3 步用的是确定性的基线，不调用模型，结果可以复现，便于评估。具体做法是：
- 用社区能力分类（可替换）里的关键词识别需求和档案；
- 已验证的交付比档案自述权重高，社区推荐另外加分；
- 每个候选人都附理由。

换成模型、接入向量检索是后续工作；在那之前，成员的 Agent 可以通过 `refine_request`（自己主人的需求）和 `suggest`（别人的需求）补充基线看不到的东西（RFC 0011 §3.4）。

## 10. 衡量方式

运营看板上的主要数字：
- 机会数、已匹配数、组成的小组数、交付数、经验证的能力数；
- 建议数、邀请接受率、从提出需求到第一个人接受所用的时间。

Agent 数量不作为主要指标。停止条件见验证计划。

## 11. 阶段

1. **让一个社区有用。** 成员自助、档案、需求、匹配、建议、预沟通、小组、验收和证据；成员 Agent 以助手身份使用第 7 节的接口。
2. **让 Agent 参与做事。** 在成员本机代为执行（已有实现）、记忆胶囊与每单沙箱（RFC 0009 提出的方案）、预沟通自动化、Agent 之间的协商。
3. **社区之间互联。** 一个社区吃不下的需求，转给愿意互联的其他社区。

## 12. 现有实现怎么处理

| 处理方式 | 内容 |
| --- | --- |
| 直接复用 | 社区与成员资格、邀请制加入、FlareMo 登录、可见范围与变更流过滤、八类对象与 FlareMo 存储、验收记录、Cloudflare Worker 版节点、RFC 0009 的档案编辑界面（改为编辑成员档案） |
| 代码保留，暂停投入 | 连接器、Codex 执行、A2A 网关、带记忆模式、沙箱与记忆胶囊方案、上线测试任务。这些属于第二阶段 |
| 第一阶段要新做 | 成员协议与签署记录、成员档案与群聊起草、需求录入与需求拆解、匹配、建议、预沟通、小组角色、运营看板、成员 Agent 的接口（说明、清单、HTTP、MCP、待办、授权令牌）、通知 |

## 13. 考虑过的其他做法

- **以运营为第一用户**（先做一个"运营副驾"）。冷启动成本最低，但维护者选择了成员自助，因为大家一起给建议本身就是价值的一部分。运营的审核视图仍然保留。
- **以 Agent 为中心的网络**：先让 Agent 互相发现、互相协商。容易变成 Agent 之间空聊，而且这一层已经有现成项目。
- **做交易市场**：公开挂单、竞价、排名。对小型社区来说太重，信任也不够。

## 14. 未决问题

1. 头一批真实需求从哪里来，由谁持续提供。
2. 成员协议的具体文本和法律审阅。
3. 共同大脑需要提供的起草接口。
4. 匹配用哪个模型，费用由谁承担。
5. 通知渠道：飞书、邮件还是网页。现有的微信工具只能读、不能发。
6. 成员接单的激励和回报方式。
7. 项目的正式名称（RFC 0001）。
