# RFC 0011 — 一个人只需要聚焦一件事

Status: Accepted by maintainer request (2026-09-23)；已实现并通过 `npm test`（95 项）与端到端评估（14/14，含真实 FlareMo 存储）。
Date: 2026-09-23
Builds on: [RFC 0010](0010-opportunity-router.md)（机会路由的定位与链路）。不改变链路本身，只改变**谁来推进它**。

## 1. 决定

> **一个人在这个网络里只需要聚焦一件事：我要什么。**
> 开头说清楚，结尾确认拿到了。中间的协调，交给他自己的 Agent 自由发挥。

具体地：

| 谁 | 他本人做的 | 他的 Agent 可以做的 |
| --- | --- | --- |
| 需求方 | ① 用一段话说出他要什么；② 最后判断交付的是不是他要的 | 把需求说清楚、邀请候选人、组队 |
| 被邀请的人 | ① 决定接不接 | 起草预沟通回答、在小组里交付 |
| 任何成员 | —— | 起草档案、给别人的需求提建议 |

两件事永远不委托，因为它们不是协调，是**承诺**和**判断**：

- **承诺**：接受邀请、投入时间或报酬 → `HUMAN_ONLY`。
- **判断**：验收交付物、签发能力证据 → `HUMAN_ONLY`。

## 2. 为什么

RFC 0010 把链路设计对了，但把**执行链路的负担留给了人**。上线前的页面有六个标签页，需求方要依次完成：签协议 → 填档案 → 填 6 个字段发需求 → 预览拆解 → 勾选候选人 → 点邀请 → 等预沟通 → 点组队 → 点验收。Agent 只在"起草"和"建议"上帮忙。

结果是：**协调成本从运营转移到了需求方本人**，而这正是 RFC 0010 说要消除的成本。一个只会在群里发一句"有没有人懂香港招聘"的人，不会走完九步。

同时，"需求明确"被当成了**准入门槛**（不写期望成果就不让发布），而它本该是**产出**：把模糊的一句话变清楚，正是 Agent 擅长、人不愿意做的事。

## 3. 改了什么

### 3.1 入口：一个输入框

`POST /api/router/requests` 接受单字段 `{ text }`：第一行成为标题，以 `-`/`*`/`1.` 开头的行成为期望成果，能力拆解由 `understand()` 自动完成。原来的 `title` / `description` / `acceptanceCriteria` 仍然接受。

`acceptanceCriteria` 不再是必填。对象协议里 `Request.acceptanceCriteria` 的 `minItems: 1` 移除——**一个还不清楚的需求应该能存在并被标记为不清楚，而不是被拒绝，或者被塞一条占位文字骗过校验。**

### 3.2 不清楚的地方被指名：`clarify`

`requestView` 对需求方返回 `clarify`：缺期望成果、缺能力拆解、缺回报方式，各自附一句"为什么这会造成问题"。同一份事实出现在三个地方：页面上的「把需求说清楚」、Agent 的 inbox 项 `request.refine`（带 `gaps`）、需求方待办里的一条。

### 3.3 `route` 授权：把中间交给 Agent

新增权限 `route`，成员在签发令牌时勾选"替我邀请候选人和组队"。**默认不勾选，API 的默认权限集也不含 `route`**（`DEFAULT_SCOPES`）：代主人向真人发邀请必须是一次明确的委托。两个动作从 `human: 'only'` 变为 `human: 'delegated'`：

- `invite_candidates`：只能用于**主人自己提的需求**；对别人的需求返回 `REQUESTER_ONLY`。
- `form_squad`：同上。

没有授权时返回 `DELEGATION_REQUIRED`（区别于 `SCOPE_REQUIRED`，因为它对应的是页面上一个具体的勾选框），inbox 里这两条自动变成"提醒主人自己处理"。由 Agent 发出的邀请，`actor.kind = 'Agent'`、`actor.principalId` 是主人，`Match.source = 'agent'`，页面上标注「由 Agent 代发」。

MCP 的 `tools/list` 现在按令牌的实际权限过滤：**Agent 看得到的工具，就是它调得动的工具。**

### 3.3.1 委托的边界（2026-09-23 补）

把邀请交给自动化，就必须给自动化划出最坏情况。实测发现原来一条都没有：Ed 拒绝后 Agent 立刻又发了一次邀请，`invite_candidates` 连调 44 次全部通过（`suggest` 早就有限流）。补上两条：

- **拒绝对自动化是终局。** 某人拒绝了这个需求，Agent 不能再邀请他（`CANDIDATE_DECLINED`）。**需求方本人仍然可以**——当面再问一次是他自己的社交成本，不是可以自动化的东西。
- **邀请有用量上限**，默认同一需求 10 人、每小时 30 人，超过返回 `RATE_LIMITED`。社区可以调低（`RouterService` 的 `limits`），清单的 `rateLimits` 公布实际值。

上限按**实际发出的邀请人数**计，不按调用次数，并且从 `Match.data.invitedByAgentId` 数出来，**不放在内存里**，所以节点重启或 Durable Object 被驱逐都不会清零。

这里还修掉一个更隐蔽的缺陷：原来"谁发的邀请"读的是实体的 `actor`，而 `next()` 会把 `actor` 换成最后一次写入的人——**被邀请的人一回应，页面上的「由 Agent 代发」标注就消失了**，用量也跟着清零。所以 `Match` 增加了一个不会被覆盖的字段 `invitedByAgentId`。它是普通数据，不是带类型的引用，因此 **FlareMo 扩展补丁仍然是 v0.2，不用重新生成**。

### 3.4 `refine_request` 取代 `propose_needs`

`propose_needs` 一个动作做两件事（主人的需求→草稿，别人的需求→建议），两种语义混在一起。现在拆开：

- 自己主人的需求 → `refine_request`（标题、期望成果、能力拆解、回报方式，任选几项），进确认队列；
- 别人的需求 → `suggest`（已有的动作，需要写理由、有频率限制）。

### 3.5 页面：六个标签页变三个

- **我要什么**：一个输入框 +「等我决定」+ 我提的需求；
- **社区机会**：别人的需求，可以推荐人；
- **更多**：档案、协议、我的 Agent、看板。

「我的邀请」和「待我确认」不再是标签页——邀请、预沟通、候选人、小组、验收现在都在**同一个需求页面**上。

### 3.6 `GET /api/router/todo`：人的唯一一份列表

和 Agent 的 `inbox` 同源，只保留本人才能做的事，每条带 `agentCovers`：已授权的 Agent 会处理的事，页面标注「Agent 会处理」，人可以不管（也可以点「我自己来」）。`review.accept` 的 `agentCovers` 恒为 `false`。

## 4. 备选方案

| 方案 | 为什么没选 |
| --- | --- |
| 节点自动邀请排名前 N 的候选人 | 确定性的关键词排序不该替人向真人发邀请；而且这是"网络替你做"，不是"你的 Agent 替你做"，成员无法约束它 |
| 保持 `invite` 只能由人做，只简化表单 | 需求方仍要盯着候选人列表。九步变七步，不解决问题 |
| 默认授权 `route`，不给开关 | 代主人向真人发邀请是有社交后果的动作，必须是成员主动勾选的 |
| 发布时强制填写期望成果 | 这正是挡住"群里一句话"的那道门槛 |

## 5. 隐私、权限与失败行为

- 授权是**按主体**的：拿到 `route` 的 Agent 也只能操作它主人自己提的需求。
- 授权是**可撤销**的：撤销令牌后立即失效（评估里有这条检查）。
- 授权是**有记录**的：每次 Agent 调用都进审计日志；由 Agent 发出的邀请在实体上和页面上都署名。
- 授权**不扩散**：`route` 不包含起草档案、提交交付物等其他权限。
- 被邀请的人不受影响：邀请是谁发的不改变"接不接由本人决定"。

## 6. 验证（决定当时，2026-09-23；当前数字以实际运行为准）

| 检查 | 结果 |
| --- | --- |
| `npm test` | 97/97 通过 |
| `npm run eval`（场景里 Mia 的 Agent 负责邀请与组队） | 14/14 阶段通过；Mia 本人只发了需求和验收 |
| 评估中的新检查 | 邀请署名为 Agent 代主人发出，并且在对方回应之后仍然成立；未授权 `route` 的 Agent 邀请被拒（`DELEGATION_REQUIRED`）；已授权的 Agent 操作别人的需求被拒（`REQUESTER_ONLY`）；有人拒绝后 Agent 再邀请被拒（`CANDIDATE_DECLINED`），且他没有收到第二份邀请 |
| 真实 FlareMo 存储（本机实例） | 同一条链路 14/14 通过 |
| 浏览器（真实 Chrome） | 一个输入框发布 → 需求页 → 拆解、缺什么、候选人、建议；无 JS 报错 |

顺带修掉一个既有缺陷：`requestView` 曾把"建议组合"（`planSquad` 的结果）写进 `squad` 字段，覆盖掉真正组成的小组，导致**需求方在页面上永远看不到自己需求的小组和交付物，也无法验收**。现在建议组合叫 `plan`，`squad` 只表示真正组成的小组。

## 7. 未决问题

- 需求文本的理解仍是关键词基线。把一段话变成清楚的需求，最终要靠成员自己的 Agent（`refine_request`）或模型；基线只保证可复现。
- `route` 是一个开关加两条用量上限（第 3.3.1 节）。是否还需要更细的约束（例如只邀请匹配分高于某个值的人），等真实使用数据。
- 没有授权 Agent 的成员，中间步骤仍由本人完成。这是设计选择，不是缺陷：网络不替没有 Agent 的人做决定。

## 8. 决定

采纳。维护者 2026-09-23 提出："代码优化，需求明确，最终用户只需要聚焦一个点，然后由他们的 agent 自由发挥。"本 RFC 把这句话变成可检查的边界：**聚焦点 = 我要什么；自由发挥的范围 = 除承诺与判断之外的全部协调。**
