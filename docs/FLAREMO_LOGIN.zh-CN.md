# FlareMo 登录与下一步

状态：本地登录入口已实现，自动化测试使用虚构的上游服务；真实实例尚未联调。它是账号密码登录实验，尚未实现 OAuth/OIDC 跳转授权、自动刷新、持久身份库或生产单点登录。设计边界见 [RFC 0004](../RFC/0004-flaremo-login.md)。

## 启动与对接

使用 Node.js 24，无新增依赖：

```sh
npm run flaremo:login
```

打开 `http://127.0.0.1:4319`。未配置时，表单禁用。配置真实实例后重启，例如将下面地址替换成获准实例的 HTTPS 根地址：

```sh
FLAREMO_AUTH_URL=https://your-test-instance.example npm run flaremo:login
```

也可在被 Git 忽略的 `.env.flaremo.local` 中填 `FLAREMO_AUTH_URL`，再运行：

```sh
node --env-file=.env.flaremo.local apps/login-demo/server.js
```

不要在配置、命令行、聊天、日志、Issue 或截图中填写账号密码。用户在本机表单中输入自己的测试账号。入口使用 FlareMo 用户名，不能用邮箱替代。服务只监听 `127.0.0.1`；不能直接作为公网登录服务发布。

请 FlareMo 管理员：

1. 确认部署提供 `/api/v1/auth/signin`、`/me` 和 `/signout`，记录版本；审阅依据为上游 `e42d98f`。
2. 将 `http://127.0.0.1:4319` 加入该实例的 `FLAREMO_TRUSTED_ORIGINS`；保留原有来源，不使用通配符。正式域名后续独立配置。
3. 确认测试账号可用，以及实例的外层访问策略允许该测试请求。当前登录实验未实现 Cloudflare Access 服务凭证接入。

我们的后端向 FlareMo 转发真实页面 Origin，不伪装为 FlareMo 自己的来源。这里是服务端调用，通常不需要浏览器直接跨域携带 Cookie，但仍受 FlareMo 来源检查约束。

## 实际流程与限制

输入账号 → FlareMo signin → 后端使用返回的访问凭证请求 me → 用实例地址与用户资源 ID 建立身份 → 浏览器获得本地会话。

- 忽略 signin 中未经再次核验的用户档案，以 me 返回身份为准。仅向页面返回最小身份摘要，不返回邮箱或凭证。
- 密码不保存；上游访问凭证和 Cookie 只保存在后端进程内存。浏览器持有 HttpOnly/SameSite=Strict 的随机本地会话 Cookie。
- 每次重新读取当前会话都向 FlareMo 核验；上游拒绝、身份变化或过期后不继续认可身份。网络异常时不返回旧的已验证档案。
- 会话最多一小时且不晚于上游访问令牌过期；没有自动刷新。重启清除本地会话，不承诺撤销 FlareMo 中已经签发的所有会话。
- 退出清除本地会话，并用该实验获得的 Cookie/凭证请求 FlareMo signout；页面说明是否获得上游成功响应。它不等于所有设备退出，也不承诺已签发令牌立即失效。
- 成员档案、社区加入、Agent 绑定、知识共享与执行授权仍未实现；登录不自动授予这些能力。

## 验收

`npm test` 覆盖合成服务下的成功路径、错误密码、来源拒绝、身份变化、上游撤权、过期、错误响应、重定向、超时及退出失败。本地模拟通过不证明真实实例可用。

真实验收由用户在页面进行：登录 → 显示正确身份 → 重新核验 → 退出 → 刷新后不能恢复会话。另用获准测试账号验证错误密码及账号停用。只记录部署版本、场景和结果；不发布账号、Cookie、令牌或未脱敏的截图。没有账号/来源白名单时，记录“待联调”，不填“通过”。

## 登录之后的开发顺序

| 顺序 | 用户能做什么 | 验收标准 |
| --- | --- | --- |
| 1. 加入社区与能力档案 | 选择获准社区、填写能提供的帮助、设置可见范围 | 两位成员能在正确范围内发现彼此；未加入者看不到私密成员资料 |
| 2. 认领 Agent | 通过一次性挑战证明控制权，声明能力并随时断开 | Agent 归属明确；挑战不能重放；断开后不能继续以成员身份使用它 |
| 3. 发现与委派 | 发布一项小需求，选择接收者，双方确认任务与资料范围 | 一次被接受的有期限委派；越权和过期请求被拒绝 |
| 4. 交付与验收 | Agent 返回成果，人确认是否完成 | 成果记录任务、Agent、负责的人与验收人 |
| 5. 选择性沉淀 | 用户选择是否把成果写入 FlareMo | 私密成果不自动发布；更新和撤回可验证 |

第一条产品闭环建议：两位成员、一位可验证的 Agent、一个小型资料整理任务、一份人工验收的结果。具体领域由试用成员的真实需求决定。平台保存成员关系、能力、授权和任务；FlareMo 保存用户选择的知识与成果。后续社区可更换身份/知识提供方，不以某个实例作为产品边界。

Build in Public 公布每一阶段的假设与验收结果；注册量和模拟输出不作为协作成效。
