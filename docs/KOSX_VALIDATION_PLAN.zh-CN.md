# 机会路由试点计划（写给 KOSX 核心成员的提案）

2026-09-22 · Agent Community 维护者起草 · 设计依据：[RFC 0010](../RFC/0010-opportunity-router.md)

**状态：第一版工具正在设计和开发，尚未上线。试点在工具就绪后开始。** 下面的目标数值都是建议值，欢迎讨论。

## 我们想验证一件事

当 KOSX 出现一个需求时，能不能比现在更快、更准地交到能把它做成的人手里，而且不再靠运营一个人记住所有人。

KOSX 已经有内容，也有人（Community & Content、People & Network），但从"我们认识很多厉害的人"到"需求出现时真的能组织起一个小组"（Projects & Delivery），中间缺了一步。这次试点就是验证能不能补上这一步。

## 试点怎么运行（约 3 周）

| 时间 | 做什么 | 谁 |
| --- | --- | --- |
| 准备 | 邀请 15–20 位核心成员，签署成员协议；系统用共同大脑里各人自己的发言起草档案，本人确认或修改（约 10 分钟） | 核心成员 |
| 第 1–2 周 | 每人至少提出 1 个真实需求（自己要做的事、手上的客户需求、KOSX Lab 项目）；看到别人的需求时推荐人选或补充；收到邀请 48 小时内回复；组队后推进 | 核心成员、运营 |
| 第 3 周 | 验收交付物；30 分钟复盘 | 全体 |

每个需求会经历：
1. 提出需求；
2. 网络把它拆成需要的能力；
3. 推荐候选人，并说明为什么推荐；
4. 大家补充建议；
5. 候选人（或他的 Agent）回答有没有空、能负责什么；
6. 本人接受；
7. 组成小组，完成交付；
8. 需求方验收。

## 需要你做的（每周约 30–60 分钟）

- 签署成员协议，确认自己的档案；
- 提出至少 1 个真实需求，或者写明"我能提供什么帮助"；
- 对别人的需求提建议：推荐人选，包括推荐你自己；
- 收到邀请后 48 小时内回复接受或拒绝；
- 复盘时说真话，好用和不好用都要说。

有 Agent 的成员可以让 Agent 帮忙起草档案、提建议、回答预沟通，但接受邀请和验收只能本人做。没有 Agent 也完全可以参加。

## 我们会看这些数字

| 指标 | 建议目标 |
| --- | --- |
| 真实需求数 | ≥ 15 个 |
| 72 小时内至少有一人接受的需求比例 | ≥ 60% |
| 组成的小组 | ≥ 4 个 |
| 完成交付并通过验收 | ≥ 2 个 |
| 档案确认率（小幅修改后确认） | ≥ 70% |
| 平均每个需求收到的社区建议 | ≥ 1 条 |

## 出现以下情况就停下来

- **两周内真实需求不到 8 个**：说明问题出在需求来源，工具帮不上。
- **邀请接受率低于 30%**：说明匹配不准，或者大家没有动力接。
- **愿意确认起草档案的人不到 40%**：说明起草方式有问题，或者隐私顾虑没有解决。

停下来也会公开结论和原因。

## 数据和隐私

- **先签署，后起草。** 签署成员协议后，才会用你在 KOSX 群里的发言起草档案；没签的人不起草。
- **起草结果先只给你看**，每一条都注明依据。你确认后才公开，任何一条都可以隐藏。
- **群聊原文不进入网络**：它留在共同大脑里，网络只保存你确认后的档案和来源编号。
- **随时可以撤回**：档案下线，起草用的数据删除，之后不再起草。
- 协议文本上线前会请法律顾问审阅。

## 想先听大家的意见

1. 你最近一次"找不到合适的人"，是什么需求？
2. 什么样的回报会让你愿意接：报酬、股份、资源交换，还是认可？
3. 你愿意让自己的 Agent 替你回答"有没有空、能做什么"吗？
4. 档案里哪些内容，你绝对不希望公开？

## 还需要一起确定

- 由谁负责持续放入真实需求（运营、KOSX Lab，还是企业对接人）；
- 试点名单；
- 开始时间，取决于第一版工具什么时候完成。
