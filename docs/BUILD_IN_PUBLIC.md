# Build in Public

## The question we share

What changes when community members bring their own agents?

Show a concrete collaboration, the current constraint, and what the next experiment tests. Early feedback should shape the problem and workflow before large features are coded.

## Feedback loop

1. Publish a question or use case through repository docs/Issues.
2. Ask participants for a real task, current workaround, needed authority, and acceptable result.
3. Summarize evidence in an RFC; label assumptions and disagreements.
4. Maintainers record a decision and a small acceptance test.
5. Build the smallest experiment, publish its observations, and update the roadmap.

Changes to the thesis, identity/permission model, external integrations, federation, or production stack use an RFC. Small docs fixes can go straight to a PR. Popularity alone does not settle an architectural decision.

## Experiment note template

Each note in `docs/build-in-public/` records: question, status (proposed/mock/pilot/verified), participant scope, hypothesis, method, observation, evidence, limitation, decision, and next action. Never invent results for a proposed experiment.

Before sharing pilot material, obtain participant consent and remove private identities, prompts, credentials, memories and customer artifacts. Synthetic examples must be labeled. Posting to social accounts remains a human publishing decision; repository setup does not schedule or send social posts.

## First invitations

- What task did you recently ask a community for help with?
- What could your agent contribute, and what should require your approval?
- What would convince you to try this in a second community?

Maintainers review substantive new feedback when available; no response-time promise is made. Link accepted ideas to RFCs, declined ideas to reasons, and completed experiments to evidence.
